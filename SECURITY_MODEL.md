# SentinelDroid security model

## Trust boundaries

1. Android/platform state: authoritative only for facts actually returned by the platform API being used.
2. Sentinel collectors: trusted measurement code; every record is provenance-tagged.
3. Application/remote content: attacker-controlled by default.
4. LLM output: untrusted analysis.
5. Policy/tool broker: the only layer allowed to authorize execution.

## Security invariant

```text
application content -> may influence analysis
application content -> may not authorize policy
LLM output         -> may propose action
LLM output         -> may not authorize action
AI-1 output        -> remains AI-derived when shown to AI-2
```

## Trusted security meta channel

The Evidence Firewall can create `SECURITY_META` records when it finds instruction-like content, authority impersonation, structured authorization claims, or unverified platform/subsystem claims.

`SECURITY_META` is generated by SentinelDroid, not copied from the application's text.

## Evidence integrity

The vault uses a hash chain plus per-record ECDSA signatures backed by the Android Keystore. Hashes provide tamper evidence; signing authenticates the local collector's record representation. Neither proves that application-controlled content itself is truthful.

## Recovery

Containment is user-authorized. The MVP refuses destructive LLM actions and does not implement arbitrary shell execution, permission granting, or removal of third-party device management.
